# A pi session as the lead: design and build plan

Written 2026-10-30. This plan assumes no prior conversation. It extends
ADR 0029, which made pi a harness for members only and listed "a pi lead"
as not built (point 9). The user chose to run the watch inside the lead
extension (section 4.6). ADR 0030 records what was built.

## 1. The goal

The user starts `pi` in a herdr or tmux pane and runs a teamwire team from
it, as a Claude Code or Codex lead does today. The lead can launch members,
send and read messages, receive results, and close the team.

AFK runs stay Claude-only. `teamwire afk start` refuses every other lead
harness (AFK-2), and this plan keeps that refusal.

## 2. What a lead needs, and where pi stands

The table lists every place teamwire asks something of the lead's harness.

| Need | Claude Code | Codex | pi today | pi plan |
| --- | --- | --- | --- | --- |
| Wiring picks the harness | `CLAUDE_CODE_SESSION_ID` | `CODEX_THREAD_ID` | never picked | `TEAMWIRE_LEAD_HARNESS=pi`, else `PI_CODING_AGENT=true` (point 4.5) |
| The CLI names the caller's session | env var | env var | `current_session` returns `None` | `PI_SESSION_ID` from the bash tool (point 4.3) |
| The MCP server names the caller's session | env var | MCP `_meta` | nothing | a variable the extension sets, checked against the parent pid (point 4.3) |
| Interactive or background | `CLAUDE_CODE_SESSION_KIND` | rollout `source` | nothing | `ctx.mode` in the state file (point 4.2) |
| Find the lead's process | `~/.claude/sessions` | thread lock | state file, members only | the same state file (point 4.2) |
| Read watch lines as they print | Monitor | no, `watch --deliver` | no | yes, the lead extension's watch tool (point 4.6) |
| Stop hook that warns of a missing watch | plugin hook | plugin hook | nothing | lead extension (point 4.1) |
| Skill and MCP server | plugin | plugin | nothing | pi package (point 4.1) |
| Resume the lead | `claude --resume` | `codex resume` | unsupported | `pi --session-id <id>` (point 4.7) |
| herdr finds the pane's session | Claude hook | Codex | herdr pi extension, path read | works already (ADR 0029 point 8) |

## 3. Facts from pi 1.4.0

Each fact comes from the docs shipped in pi 1.4.0
(`node_modules/@earendil-works/pi-coding-agent/docs/`) or its `dist/`
source. None has been seen in a live lead session yet.

| Fact | Source |
| --- | --- |
| pi sets `AI_AGENT=pi` and `PI_CODING_AGENT=true` in its own environment, so every child process inherits them. | `environment-variables.md` |
| The bash tool adds `PI_SESSION_ID` and `PI_SESSION_FILE` to each command, read fresh at each command. Commands a person types with `!` do not get them. | `environment-variables.md`, `dist/core/tools/bash.js` |
| MCP servers get no session variable. pi strips `_meta` from results and sends none with requests. | `dist/extensions/mcp/tools.js` |
| `pi install <local path>` records a package in `~/.pi/agent/settings.json` and loads it from that path without copying. `pi remove <path>` undoes it. | `packages.md` |
| A package may hold `extensions/` and `skills/`. pi lists each skill's name and description in the system prompt. | `packages.md`, `skills.md` |
| `pi.registerMcpServer` throws when another extension already registered the same name. A server registered after load connects right away. | `extensions.md` |
| MCP tools default to `codemode` exposure, reachable only from scripts. `exposure: "direct"` declares them to the model like built-in tools. | `mcp.md` |
| Extensions load in interactive, RPC, JSON and print modes. `ctx.mode === "tui"` marks the interactive terminal UI. | `extensions.md` |
| `--session-id <id>` opens the session with that id in the current folder, or makes a new one. | `cli.md` |
| No run option turns off a single package. `--no-extensions` turns off all of them, including a member's model provider. | `cli.md` |

The last fact shapes the design. A pi member loads the user's packages
(ADR 0029 point 3), so the lead package also loads inside every pi member.
The lead extension must switch itself off there.

## 4. Design

### 4.1 The lead package

`teamwire install` writes a pi package to `$TEAMWIRE_HOME/pi-package/` and
registers it with `pi install <that absolute path>`. `teamwire uninstall`
runs `pi remove <path>`. teamwire changes pi's setup only through these two
commands, the way it changes Codex's setup only through `codex plugin`.

```
$TEAMWIRE_HOME/pi-package/
├── package.json              {"name": "teamwire-lead", "pi": {...}}
├── extensions/teamwire-lead.ts
└── skills/teamwire/
    ├── SKILL.md              shared skill text plus a pi part
    └── reference.md
```

The lead extension does these things, all decided at `session_start`:

1. It checks for `TEAMWIRE_ROLE` or `TEAMWIRE_TOKEN_FILE` in
   `process.env`. The member extension sets both when it loads, and every
   extension loads before the first `session_start`. When either is set, the
   lead extension does nothing more. The member extension has already
   registered its own `teamwire` server, so a second registration would
   throw.
2. It registers the MCP server `teamwire` as `<bin> [--home H] mcp --lead`,
   with `exposure: "direct"`, so the skill's `mcp__teamwire__team_*` names
   reach the model without a codemode script.
3. It writes the lead's state file (point 4.2).
4. On `agent_before_settle` with outcome `completed`, it runs
   `<bin> [--home H] hook lead-stop --harness pi` with the same stdin the
   member extension sends to `hook turn-end`. A `block` reply becomes a
   `custom_message` with `continue: true`, as in the member extension.
5. It registers the `teamwire_watch` tool and refuses a bash call that
   runs `teamwire watch` (point 4.6).

The template lives in `teamwire-harness-pi`, beside the member template,
and shares the state-file and settle code with it. The CLI passes in the
shared skill text, because one adapter crate may not depend on another.

### 4.2 The lead's state file

The lead extension writes
`<agent_dir>/sessions/teamwire/<id>.teamwire.json`, the folder and format
members already use. The adapter's `processes_for_session` and `is_alive`
then work for the lead unchanged. The lead's state file adds three fields:

| Field | Why |
| --- | --- |
| `session_file` | The lead's session file lives in pi's own folder for the cwd, not in `sessions/teamwire/`. `session_cwd` and `context_fill` read it from here. |
| `mode` | `ctx.mode`. Only `tui` counts as an interactive session. |
| `lead: true` | Keeps a lead's file apart from a member's when a reader lists the folder. |

A `/new` or `/resume` inside the lead ends the old session's file with
`ended` and starts a new file, as for a member. The team then records an
old session, so the lead runs `teamwire lead --adopt`. A Claude lead after
`/clear` is in the same position.

### 4.3 How a pi lead proves itself

The adapter's `caller_session` reads the session from one of two places:

1. **`PI_SESSION_ID`.** Every `teamwire` command the lead runs through its
   bash tool has it. The kind is `Interactive` only when that session's
   state file says `mode: "tui"` and its pid is alive. Every other case is
   `Background`, so a missing package can never prove a lead.
2. **The MCP server's variable.** The lead extension registers the
   server with `TEAMWIRE_PI_LEAD_SESSION` set to the session's id, and
   registers it again for a new session. The adapter reads that session's
   state file and accepts it only when the recorded pi process is the
   server's parent, read through `Platform::parent_of`.

The server's variable is read first, because pi may have inherited a
`PI_SESSION_ID` from the shell it started in. Only MCP calls pay for the
`ps` that reads the parent, and every call reads one state file.

### 4.4 Capabilities

`reads_watch_lines` becomes `true`, because the lead extension hands each
watch line to the model (point 4.6). Launch therefore prints
`teamwire watch <team>` for a pi lead and skips the locator check that
ADR 0023 point 9 adds for a lead that cannot read watch lines.

A pi lead without the lead package would have no watch tool, so nothing
would reach it. `Harness` gains `lead_setup_missing()`, and pi returns a
reason when it finds no lead session. Launch of a new team refuses with
`lead_setup_missing`.

### 4.5 Wiring

`lead_harness` in `crates/teamwire-cli/src/wiring.rs` changes to this order:

1. `TEAMWIRE_LEAD_HARNESS`, now also accepting `pi`.
2. `claude-code` when `CLAUDE_CODE_SESSION_ID` is set.
3. `codex` when `CODEX_THREAD_ID` is set.
4. `pi` when `PI_CODING_AGENT` is `true`.
5. `claude-code` otherwise.

pi comes last because its marker is inherited by everything pi starts. A
Claude or Codex lead started from a pi shell carries its own variable, and
that variable wins.

A member with no `harness` in the spec runs on the lead's harness (ADR 0023
point 1). Under a pi lead, such a member runs on pi.

### 4.6 Results and watch lines

The lead extension registers a tool, `teamwire_watch` `{team}`. The tool
starts `teamwire watch <team>` as a child of pi. Each line the watch prints
goes to the model through `pi.sendMessage` with `triggerTurn: true` and
`deliverAs: "steer"` (ADR 0036). pi starts a turn for the line when it is
idle, and delivers it after the current turn's tool calls when it is not.

- The tool waits up to 2 s, so a watch that is refused at once, such as a
  second watch of the team, fails the call with its message.
- A watch that ends later with a non-zero code sends one line that says so.
- `session_shutdown` stops the watches of the process. A quit, `/reload`,
  `/new` and `/resume` all fire it, and the lead starts the watch again.
- The extension refuses a bash call that runs `teamwire watch <team>`
  without `--once`, and its reason names the tool. Such a call would hold
  the bash tool until it timed out.

Results still reach the lead by typing into its pane when the host can type
(ADR 0007).

### 4.7 Resume

`lead_resume_argv` returns `pi --session-id <id>`. `teamwire reopen` runs
it from the folder that `session_cwd` names, because pi looks the id up in
the current folder's sessions.

### 4.8 Doctor

Doctor reports the lead package when `pi` is on PATH:

| Case | Level | Hint |
| --- | --- | --- |
| Not installed | `ok` | the `teamwire install --harness pi` command |
| Installed, files out of date | `warn` | the same command |
| Installed and current | `ok` | none |

The check for herdr's pi integration stays as it is.

## 6. Facts checked, and facts still open

A run of real pi 1.4.0 against a temporary `PI_CODING_AGENT_DIR`, with no
model call, showed these facts:

- `pi install <dir>` lists the package as a path relative to pi's folder.
- `pi --help` loads the package with no error.
- `pi --mode rpc` starts a session in which the lead extension writes its
  state file and starts `mcp --lead`.
- `new_session` ends the first state file and writes a second.
- The MCP server's parent pid is the pid in the state file.

A live end-to-end run with a pi lead in a private tmux server then passed:
launch, the watch tool, the member's result typed into the lead's pane,
`verify`, `close`, a watch line starting a turn in the idle lead, and an MCP
call that proved the lead by its parent process. ADR 0030 has the details.

Still open:

1. A watch line starts a turn while a person has text in the input box,
   without taking that text.
2. A line queued during a run reaches the model when the run ends.
3. A lead-stop `block` reply reaches the model as one more turn. ADR 0029
   lists the same open fact for members.

## 7. Not in this plan

- AFK runs from a pi lead.
- OpenTelemetry settings for pi.
