# Task: build AFK mode for teamwire

teamwire needs AFK runs: a lead runs one team on one task while the user is away, with no questions to the user until a report is written.

The design and build plan are in `docs/design/2026-10-19-afk-mode.md`. Read all of it first. Schema version 5 (`team.afk_budget_ends_at`) is already committed, as the plan's "Precondition" says.

End state: everything that sections 5 and 6 of the design describe exists and is tested.

- `teamwire afk start` (section 5.2).
- The AFK hold in the lead's Stop hook (section 5.3).
- The budget and the model table in launch (section 5.4).
- Close and status for AFK teams (section 5.5).
- The AFK skill with the agreed content of section 6, installed the way the other skills are (section 5.6).

Use the command names, flags, refusal codes and messages that the design gives. Where the design leaves a detail open, decide it and say what you decided in your final message.

## Names the design does not give

Use these names, which the rest of the code will rely on:

- `teamwire afk start` refuses with these codes, in addition to the ones the design names:
  - `no_lead_session` when no lead harness session id reaches the command.
  - `no_lead_process` when the platform needs a sleep hold and the lead's process cannot be found. Nothing is created.
  - `afk_already_running` when the calling session already leads an open AFK team.
  - `doctor_failed` when a doctor check fails. The refusal names the check.
- Crate `teamwire-report` exports `afk_hold_notes(home: &Path, session: &SessionId, platform: &dyn Platform, clock: &dyn Clock) -> Vec<String>`, beside `teams_without_watch` and `watch_missing_note`. It returns the AFK hold notes for the open AFK teams that `session` leads, when nothing will wake the lead: no open team the session leads has both a working member and a live watch lease.
- Crate `teamwire-store`: `create_afk_team` takes a fourth parameter, `create_afk_team(at, team: &NewTeam, budget_ends_at, extra: &serde_json::Value)`. The keys of `extra` are merged into the data of the `team.created` event. `teamwire afk start` passes `{"lead_cwd": <the lead's working directory>}`.
- Crate `teamwire-watch`: `StatusView` gets `afk: Option<AfkView>`, `None` for a team that is not an AFK run. `AfkView` has the fields `budget_ends_at: Timestamp`, `seconds_left: u64` (zero once the budget is spent), `spent: bool` and `decisions: u32` (the number of `D<n>` entries in `afk/decisions.md`). `status --json` writes the same field names.
- `teamwire teams --json` gives each team an `afk_budget_ends_at` key: a timestamp string for an AFK team, `null` otherwise. The dashboard's zod schemas in `ui/src/shared/teamwire.ts` accept the `afk` object and this key, and also accept older output without them.

+                path.display()

+/// The lowercase text of a markdown heading line (one to six `#`, a space),
+/// without a leading `N.` or `N)` and without `**`.
+fn heading_text(line: &str) -> Option<String> {
+    let rest = line.trim_start_matches('#');
+    let hashes = line.len() - rest.len();
+    if !(1..=6).contains(&hashes) {
+        return None;
+    }
+    let rest = rest.strip_prefix(' ')?.replace("**", "");
+    let rest = rest.trim_start();
+    let digits = rest.trim_start_matches(|c: char| c.is_ascii_digit());
+    let rest = match digits.strip_prefix(['.', ')']) {
+        Some(after) if digits.len() < rest.len() => after,
+        _ => rest,
+    };
+    Some(rest.trim_start().to_lowercase())
+}

+pub fn afk_check(

+pub fn afk_hold_notes(

+    clock: &dyn Clock,
+) -> Vec<String> {
+    let names = team_names(home).unwrap_or_else(|e| {
+        tracing::warn!(error = %e, "the teams could not be listed");
+        Vec::new()
+    });
+    let now = clock.now();

+    for name in names {
+        match led(home, &name, session, platform, now) {

+            }

+/// `None` when the team is not open or not led by `session`.
+fn led(
+    home: &Path,
+    team: &TeamName,
+    session: &SessionId,
+    platform: &dyn Platform,
+    now: Timestamp,
+) -> Result<Option<Led>, StoreError> {
+    let store = Store::open_read_only(home, team)?;
+    store.read(|tx| {
+        let Some(row) = tx.team()? else {
+            return Ok(None);
+        };
+        if row.state != TeamState::Open || row.lead_session.as_ref() != Some(session) {
+            return Ok(None);
+        }

+            .watch_lease()?
+            .is_some_and(|lease| !watch_lease_is_dead(&lease, platform, now));

+            afk_ends: row.afk_budget_ends_at,
+            wakes_lead: watched && has_working_member(tx)?,
+        }))
+    })

+# ADR 0025: An AFK run is one ordinary team, started by `teamwire afk start`
+
+Status: accepted, 2026-10-27. Builds on ADR 0002 (one team is one directory
+and one database), ADR 0006 (locating the lead), ADR 0015 (read-only opens)
+and ADR 0018 (teamwire is a Claude Code plugin). The design is
+`docs/design/2026-10-19-afk-mode.md`.
+
+## Context
+
+A user types one task and walks away. The lead session then has to research,
+plan, run a team, verify the result and write one report, with nobody to
+answer a question. Before this ADR the lead had four ways to stall:
+
+- It ended a turn with a question to the user, and nothing woke it again.
+- The Mac slept during planning, before any member existed, because launch
+  takes the sleep hold only when the first member starts.
+- A lead that kept re-planning ran all night, with no limit.
+- The lead read every result itself, so its context filled up in a long run.
+
+Members already work with nobody present. They start with bypassed
+permissions, their contract says no human is watching, and a question to the
+lead does not block them. So the work is on the lead's side.
+
+## Decision
+
+1. **An AFK run is one ordinary team.** Its `team` row has
+   `afk_budget_ends_at` set (schema version 5). The value is when the budget
+   ends, so one nullable column says both that the team is an AFK run and
+   when it must stop. Every reader looks at the same row it already reads.
+2. **Every member joins that one team with `teamwire launch --add`.**
+   Investigators, the plan reviewer, implementers, the reviewer and the
+   closer all use the run's team. The team keeps one sleep hold, one archive,
+   one set of metrics and one Stop hook check.
+3. **`teamwire afk start --team NAME --title TITLE --task FILE [--budget
+   DURATION]` creates the team.** The command runs only from the shell. It
+   finds the lead session as launch does, checks the name, title and budget,
+   runs the checks of `teamwire doctor` that a launch needs, creates the team
+   with no members, copies the task to `afk/task.md`, takes the sleep hold
+   and prints where the run lives. The budget uses the units of
+   `metrics --since` and defaults to `8h`. The team exists from the start of
+   planning, so the sleep hold covers planning too.
+4. **The run's files live in `$TEAMWIRE_HOME/teams/<team>/afk/`.** Close
+   already copies every file of the team directory into the archive, so these
+   files reach the archive with no new code. The path avoids `reports/`,
+   which belongs to members and is checked per role.
+5. **The lead's Stop hook holds the stop for an AFK team.** The hook
+   already walks every open team the session leads. It now also holds once
+   per stop chain when an open AFK team exists and nothing will wake the
+   lead: no started member without a completion has a live watch. It skips
+   the hold when `stop_hook_active` is true, so a lead with a command of its
+   own that will wake it can stop. A counter would hold forever or need extra
+   state. Past the budget the note says the budget is spent.
+6. **Past the budget, launch refuses new implementers.** The refusal is
+   `afk_budget_spent`. Every other kind still starts, so the run can review,
+   verify and report on what it built. New code is what drags a run on,
+   because each implementer brings a review, fix rounds and verification.
+   Launch also warns about each member of an AFK team whose model or effort
+   is below the AFK table in the skill.
+7. **A run ends with `teamwire close <team>`.** Close refuses an AFK team
+   whose `afk/REPORT.md` is missing or lacks one of the eight required
+   headings, with `afk_report_incomplete`. A `--role` removal is unaffected.
+   No flag overrides the check, because a lead that wants out writes the
+   eight headings. A team that never had a member has nothing to report, so
+   close accepts it without the file. That covers a start that failed after
+   it created the team, and a run that ended before the first launch. A team
+   whose only member was removed still needs the report.
+8. **`teamwire status <team>` shows the run.** One more line gives the
+   budget end, the time left and the number of entries in `afk/decisions.md`.
+   `--json` gets an `afk` object, and `teamwire teams` marks an AFK team.
+9. **The skill is a second skill of the Claude plugin.** The file
+   `examples/skills/afk/SKILL.md` is rendered as `skills/afk/SKILL.md` by
+   `teamwire install`, so Claude Code lists it as `/teamwire:afk`. The
+   plugin version hashes every rendered file, and doctor's plugin check
+   compares every rendered file, so a changed skill is a new version and
+   an edited copy is a problem. The main skill gets one pointer line.
+10. **AFK runs are supported only for a Claude Code lead.** The skill is
+    installed in the Claude plugin only. `teamwire afk start` does not refuse
+    another harness, so a Codex lead can start a run that nothing supports.
+    Codex has its own lead skill and has never run live.
+
+## Options rejected
+
+- **A separate AFK home**, such as `$TEAMWIRE_HOME/afk/<run>/` with its own
+  state. Every reader of team state would need a second place to look: status,
+  watch, close, the Stop hook, metrics, the dashboard. One team row with one
+  nullable column gives the same facts with one added check in each reader.
+- **An `afk finish` command.** Close already ends a team in the safe order and
+  releases the hold. A second ending command would duplicate that order.
+- **An `afk status` command.** The run is a team, so the team's status is the
+  run's status.
+- **Several teams in one run.** The main skill already says to start a new
+  team only for work that will not be integrated with this one. One team keeps
+  the hold, the archive, the metrics and the Stop hook check on one row.
+- **A counter for the Stop hook hold.** It would hold forever or need extra
+  state. Once per stop chain is the rule the existing hold already follows.
+- **A token budget.** The user chose a wall-clock budget only.
+- **A new field on `NewTeam`.** 34 callers in 26 files build a `NewTeam`.
+  The store has a separate `create_afk_team` that sets the column.
+
+## Consequences
+
+- A team can have no members. Status, watch, close, reopen, verify, metrics
+  and the dashboard must work for it. The watch prints `TEAM-COMPLETE` only
+  when at least one member has settled, so an empty team stays quiet.
+- An older binary refuses an AFK team's database, even for a read-only open,
+  with the schema-newer error. ADR 0015 point 4 already says so for any newer
+  schema.
+- The hold cannot see a background command that the lead started itself.
+  The note tells the lead to stop again in that case, and the next stop
+  passes. A lead that stops twice with nothing running is stuck, and
+  `teamwire status` shows the AFK team open with no working member.
+- A Claude usage limit pauses every session, members and lead alike. The
+  report's cost section makes the stop visible afterwards.
+- The run never pushes, opens a pull request or merges into the base branch.
+  The result is a local integration branch that passed the full gate.

+name: afk

+# AFK runs with teamwire
+
+You lead a teamwire team on one task, and nobody will answer you until the
+run ends. Read the teamwire skill first. This file lists only what changes,
+and where the two disagree, this file wins.
+
+## The one rule
+
+Never wait for a person. When you would ask the user something, answer it
+yourself with the answer you would have recommended, write it into the
+decision log, and carry on. A turn that ends on a question to the user ends
+the run, because nothing will wake you again. Step 1 is the only place you
+may stop for the user.
+
+## 1. Preflight, while the user may still be at the keyboard
+
+1. Check that your context says bypass permissions mode or auto mode is
+   active. If it does not, tell the user to restart the session with
+   `claude --permission-mode bypassPermissions`, and stop.
+2. Write the user's task, word for word, to a file. Pick a team name and a
+   title from the task. Run the command below. Add `--budget` only when the
+   user named a time limit. It takes a whole number and one unit, such as
+   `30m`, `8h` or `1d`, and defaults to `8h`.
+
+   ```
+   teamwire afk start --team <name> --title <title> --task <file>
+   ```
+
+3. Read the result. A refusal prints `refused: <code>: <message>` and
+   `nothing was created` on stderr, and exits 1. A line that starts with
+   `failed:` exits 2. When it names a team, that team now exists without
+   its task copy. In both cases, tell the user what failed and stop. A line that
+   starts with `warning:` is not a refusal. Carry on, and put the warning in
+   the report.
+4. On success the command prints five lines and exits 0:
+
+   ```
+   team <team>: AFK run started
+   afk dir: <home>/teams/<team>/afk
+   report: <home>/teams/<team>/afk/REPORT.md
+   budget ends: <time, RFC 3339 UTC>
+   Keep the lid open and the machine on power: a closed lid still sleeps a Mac.
+   ```
+
+   Reply once, quoting the team name, the report path and the time the
+   budget ends, and add: "Keep the lid open and the machine on power." Then
+   start section 2 in the same turn. Do not wait for an answer.
+
+The run is this one team. Every member you add later joins it with
+`teamwire launch --add`. Never start a second team for this run.
+
+## 2. What every run must have
+
+You choose the team for each task. These five things hold in every run, and
+nothing in the task changes them:
+
+1. You never wait for a person (the one rule above).
+2. You protect your own context (section 3).
+3. Once code exists, the `closer` runs. It runs every claimed check and the
+   repository's full gate on each branch and on the joined branch, and
+   records each exit code. It is the only member that turns the team's
+   claims into evidence before the user reads the report.
+4. A `reporter` writes `afk/REPORT.md` (section 7). Close refuses the team
+   until the report has every heading.
+5. The boundaries hold: never push, open a pull request, merge into the base
+   branch, delete a branch, or run `teamwire install` or `cargo install`.
+   Never act on a team this session does not lead.
+
+Everything else is yours to decide: which members to add, how many, and in
+what order.
+
+## 3. Your context is the run's scarcest resource
+
+You decide. Members research, plan, review, verify and write. Every file you
+read stays in your context for the rest of the run, and a lead with a full
+context decides worse. So:
+
+- Give research, planning, review, verification and report-writing to
+  members. Do one yourself only when it is smaller than writing its brief,
+  and never reading more than one or two short files.
+- Pass work by path. A brief or a reprompt names files. Never paste a
+  report, a diff or a log into a message.
+- Read a member's result line and the summary at the top of its report. Read
+  further only when two members contradict each other, and then only the
+  lines in dispute.
+- Never read a raw diff, check output or a gate log. The closer reads those.
+- Members read each other's files by path. A planner reads the
+  investigators' reports, a plan reviewer reads the plan, and each owner
+  reads its own findings.
+
+Each member you add runs once and finishes. None of them sends work to
+another member. You make every call that changes the plan.
+

+

+needs. When you are unsure whether a member pays for itself, add it. One

+```

+

+```

+## What I understood

+The branch, its base commit, the commits, and how to try it.
+## Verified
+Each command, where it ran, and its exit code.
+## Decisions made for you
+The ones that most change the result, with a pointer to decisions.md.
+## Not done, and why
+Each unit that was cut, and the reason.
+## Risks
+What you could not check, and what the reviewer or closer flagged that is still open.
+## Cost
+Wall time, and tokens per member.
+```
+

+reply. Close accepts a team that never had a member. A team that had a
+member, even a removed one, still needs the report.
+
+A run always ends with a report. When something fails that nobody can fix,
+have the reporter write up what exists. A partial result with an honest
+report is the goal. A session waiting for a person is the failure.
